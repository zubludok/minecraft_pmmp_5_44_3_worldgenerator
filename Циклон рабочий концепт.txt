	# 1. Назначение системы
	WG во время генерации мира рассчитывает климатические и погодные параметры каждого сектора и сохраняет 
	результат в отдельный файл weather.
	WET во время игры загружает этот файл и использует сохранённые правила и параметры, чтобы определить 
	текущее состояние погоды в зависимости от игровой даты, времени суток и текущего положения игрока.
	Граница ответственности:
		WG: 
			ландшафт:
			базовая температура → базовый ветер → исправление температуры → годовые состояния → сезонные состояния → 
			суточные состояния → влажность → возможные явления → weather.
		WET: 
			текущая дата / время → текущее состояние погоды → положение игрока/обьекта → воздействие.

	# 2. Настройки климата мира
	Перед запуском этапа формирования погоды игрок задаёт параметры:
		1. Температура полюса, это температура крайних северных и южных секторов.
		2. Температура экватора, это температура двух центральных рядов секторов. 
		Экватор и полюса являются географически фиксированными и не смещается при расчётах.
		3. Смещение температурного профиля.
		Целое значение: -N 0 +N.
		4. Общая влажность климата, где -1 0 +1 от нормы.
	N - максимальное количество секторов от экватора до соответствующего полюса.
	Отрицательное значение смещает тёплый температурный профиль к северу (север остаётся на месте, уменьшается сектор градиента).
	Положительное - к югу.
	Смещение на юг работает зеркально.
	Для влажности -1 означает абсолютную сухость климата, 1 вечный "дождь".

	# 3. Ограничения карты
	Для упрощения климатической модели:
		- количество секторов по высоте всегда чётное;
		- количество секторов по ширине всегда чётное;
		- минимальный размер карты - 8 × 8 секторов.
	Карта делится на два одинаковых полушария:
		Северное полушарие (один ряд)
		------------------
		Экватор (два центральных ряда)
		------------------
		Южное полушарие (один ряд).

	# 4. Временная модель
	Погода имеет четыре временных уровня:
		- Сутки. Один игровой день = игровые сутки, разделен на: день / ночь (D/N)
		- Сезон. Состоит из 30 игровых суток. Должно быть 4 сезона: весна, лето, осень, зима. 
			Сезон ограничивается соответствующим полушарием.
			Например: ЕСЛИ Север: лето, ТО Юг:зима
		- Год. 4 игровых сезона = 120 игровых суток.
			Один игровой год должен соответствовать примерно 10 реальным дням.
			Существуют три климатических состояния года: cold-холодный, normal-обычный, hot-жаркий
			Тип года изменяется в соответствии с межледниковым циклом.
		- Межледниковый цикл
			Один межледниковый цикл = 3 игровых года.
			Это примерно 30 реальных дней.

	# 5. Основная модель - Циклон
	Циклон - это алгоритм для согласованной климатической карты.
	Циклон используется в следующих режимах:
		- Первичная погодная карта
		- Сезонный проход
		- Суточный расчёт
		- Влажность
		- Явления
	Циклон становится активным после перехода на WG этап разделения на острова.
	И далее кнопка следующий этап выполняет:
		1	Анализ ландшафта				Высоты, вода, суша, песок
		2	Базовые климатические карты		NORMAL, HOT, COLD, температура и НКСВ
		3	Сезонные проходы				12 состояний: 3 типа года × 4 сезона
		4	Суточный расчёт					Дневной и ночной ветер, температура, устойчивость
		5	Расчёт влажности				Влажность каждого сектора для 12 состояний
		6	Погодные явления				Дождь, снег, туман, бури и регионы
		7	Экспорт							Полный weather.json
	Клавиши: 
		следующий ход - смена отображения года
		цикл - смена отображения сезона
		новая клавиша - смена отображения D/N
		новая клавиша - смена отображения ветер,влажность,температура.
		
	# 6. Этап 1 - Initial Первичная погодная карта
		Формирует стандартную исходную погодную карту для каждого сектора.

		## 6.1. Географическая привязка температуры
			- Экватор - два центральных ряда секторов. Температура задаётся параметром - getEquatorTemperature.
			- Полюса - крайние ряды (северный и южный). Температура задаётся параметром - getPolarTemperature.
			- Экватор и полюса географически фиксированы, но есть расширение температуры экватора к одному из полюсов. 

		## 6.2. Смещение температурного профиля
		Смещение задаётся параметром - PolarShift и изменяет только положение границы градиента, но не положение экватора.
			= 0 - симметричный градиент.
			< 0 - расширение тёплой зоны к северу.
			> 0 - расширение тёплой зоны к югу.

		## 6.3. Формула температуры
		Для северного полушария (z от 0 до northEquatorZ):
			if z >= northGradientEnd:
				T = T_equator
			else:
				position = 1 - (northGradientEnd - z) / northGradientEnd
				position = clamp(position, 0, 1)
				T = T_polar + (T_equator - T_polar) * position
		Для южного полушария - зеркально, от sizeZ-1 к southGradientEnd.

		## 6.4. Формула коэфициента скорости.
		НКСВ экватор 1, полюс 0. В секторах между ними градиент.
		ЛКСВ увеличивается если поверхность выше waterLevel за каждый слой 0.01.
		ИКСВ = НКСВ + ЛКСВ.
		На основе Initial сразу формируются три климатических состояния года: Нейтральный, Жаркий, Холодный. 
		G = (T_equator - T_polar) / TEMP_SCALE
		Жаркий год: тянем полюс к экватору, экватор слегка поднимаем
			Δ_hot_polar    = +G * MOVE_HOT_POLAR_PULL * (T_equator - T_polar)
			Δ_hot_equator  = +G * MOVE_HOT_EQUATOR_LIFT * (T_equator - T_polar)
		Холодный год: тянем экватор к полюсу, полюс слегка опускаем
			Δ_cold_polar   = -G * MOVE_COLD_POLAR_DROP * (T_equator - T_polar)
			Δ_cold_equator = -G * MOVE_COLD_EQUATOR_PULL * (T_equator - T_polar)
			Initial_NORMAL = gradient(T_polar, T_equator)
			Initial_HOT    = gradient(T_polar + Δ_hot_polar, T_equator + Δ_hot_equator)
			Initial_COLD   = gradient(T_polar + Δ_cold_polar, T_equator + Δ_cold_equator)
		Для жаркого и холодного года создаются отдельные карты.

		## 6.5. Результат
		Получаем три исходные карты: Initial_NORMAL, Initial_HOT, Initial_COLD.
		Каждая карта с температурой для каждой (x, z) и коэфициентом скорости.

	# 7. Этап 2 - Seasonal Сезонный проход
		Сезонный проход создаёт для каждого года - четыре сезона со своей погодой.

		## 7.1. Движениие Циклона по сезонам
		Для каждого типа года выполняется отдельный сезонный расчёт.
		Получаем: 3 типа года × 4 сезона = 12 состояний.
		Расстояния перемещения Циклона зависят от ширины и высоты карты. 
		Движение Циклон для получения разных погодных условий разделяется на полярное и экваториальное движение следующим образом:
		Северное полушарие:
			Лето:
			Экваториально движение: Циклон движется от экватора со смещение в право и вверх (0:5,1:4,2:3...), 
			до 3/4 полушария.
			Полярное движение: Циклон движется от полюса со смещением назад и вниз (0:0,9:1,8:2...) до 1/4 полушария.
			Осень:
			Экваториально движение: Циклон движется до 1/4 полушария.
			Полярное движение: Циклон движется до 2/4 полушария.
			Зима:
			Экваториально движение: Циклон движется до 1/4 полушария.
			Полярное движение: Циклон движется до 3/4 полушария.
			Весна:
			Экваториально движение: Циклон движется до 2/4 полушария.
			Полярное движение: Циклон движется до 1/4 полушария.
		Для южного полушария траектории являются вертикальным отражением северных.
		Для каждой карты циклон проходит четыре участка: сначала от экваториальных секторов, затем от полярных. 
		Каждый проход разбит на отдельные цепочки.
		Суммарное количество цепочек прохода = ширина карты × 4.
		Длинна каждой цепочки определяется долей описанной выше. 
		То есть, для полушария высотой 12 секторов: 
			Летняя цепочка экваториального движения 9 секторов.
			Летняя цепочка полярного движения 3 сектора.
		Это позволяет обработать все стартовые позиции, не смешивая сезонные состояния полушарий.
		Если происходит наложение, результат просто перезаписывается.
		WET будет определять сезон по северному полушарию и автоматически выбирать противоположный сезон для южного.
		
		## 7.2. Правило движения и изменения погоды Сезонного этапа.
		Циклон использует 3 сектора за раз: исходная → целевая → следующая (S→T→N).
		При начале цепочки Циклон использует в качестве S сектор слева от сектора T.
		Далее сектором S является тот, который был T.
		Правило переноса тепла и холода:
		Берётся каждый раз для сезона из исходной карты по 2 параметра из S, T, N: температура и ИКСВ.
			- St температура сектора S. 
			- Tt температура целевого сектора. 
			- Nt температура следующего сектора.
			- Si ИКСВ S. 
			- Ti ИКСВ T. 
			- Ni ИКСВ N.
			- СТ.
			- СКСВ.
			- TRANSFER_BASE
			- TEMP_REFERENCE
		Веса:
			w_s = Si / (Si + Ti + Ni) вклад источника
			w_t = Ti / (Si + Ti + Ni) вклад цели
			w_n = Ni / (Si + Ti + Ni) вклад следующего
		Средневзвешенная температура потока:
			T_flow = St * w_s + Tt * w_t + Nt * w_n
		Отклонение цели от потока:
			delta = T_flow - Tt
		Передача: сектор сам решает, сколько взять:
			transferRate = TRANSFER_BASE * Ti 
			Ti ∈ [0,1] - чем выше ИКСВ, тем сильнее реакция:
			СТ = Tt + delta * transferRate
			Скорость ветра не передаётся от S и N, а формируется локально в T под влиянием перепада температур. 
			Чем сильнее поток контрастирует с целью, тем быстрее он через неё проходит.
		Температурный градиент между потоком и целью:
			gradient = |T_flow - Tt|
		Базовый коэффициент скорости цели:
			base = Ti
		Ускорение от градиента (нормируем на типичный перепад):
			gradientBoost = gradient / TEMP_REFERENCE 
			gradientBoost = clamp(gradientBoost, 0, 1)
			СКСВ = clamp(base + gradientBoost * WIND_SPEED_BOOST, 0, WIND_SPEED_MAX)

		## 7.3. Сезонное направление ветра.
		СНВ задается проходом Циклона в секторе.
		Это касательная к траектории Циклона в точке T. Не среднее, не интерполяция - просто геометрия маршрута.
			dx = N.x - S.x
			dz = N.z - S.z
			if (dx == 0 && dz == 0): вырожденный случай - берём направление от S к T
				dx = T.x - S.x
				dz = T.z - S.z
		СНВ = atan2(dx, -dz) в градусах, нормализовать в [0, 360)

		## 7.4. Итоговые данные.
		Для каждого сектора получается:
			- NORMAL:spring(СТ, СКСВ, СНВ),summer(СТ, СКСВ, СНВ),autumn(СТ, СКСВ, СНВ),winter(СТ, СКСВ, СНВ).
			- HOT:spring(СТ, СКСВ, СНВ),summer(СТ, СКСВ, СНВ),autumn(СТ, СКСВ, СНВ),winter(СТ, СКСВ, СНВ).
			- COLD:spring(СТ, СКСВ, СНВ),summer(СТ, СКСВ, СНВ),autumn,winter(СТ, СКСВ, СНВ).

	# 8. Этап 3 - суточный расчёт
		Формирует для каждого сектора дневное и ночное состояние погоды на основе сезонных данных.
		На этом этапе:
			- каждый сектор обрабатывается локально, в радиусе 1 сектора.
			- результатом являются два набора значений TDW - для D/N.
			- вместе с ними сохраняются два параметра устойчивости: holdTime и stability_dynamic.

		## 8.1. Входные данные
		Для каждого из 12 сезонных состояний (yearType × season) сектор имеет:
			- temperature - сезонная температура (СТ).
			- direction - сезонное направление ветра (СНВ).
			- wind - сезонный коэффициент скорости ветра (СКСВ).
		Дополнительно WG берёт из ландшафтной карты:
			- Hs(x, z) - высоту сектора над waterLevel.
			- Hn(x', z') - высоту всех 8 соседей в радиусе 1.
			- тип поверхности каждого соседа - вода или суша.
			- sign - полушарие сектора (северное / южное).
		Все входные данные берутся из сезонных карт и ландшафта, а не из промежуточных результатов суточного расчёта. 
		Это гарантирует независимость от порядка обхода.

		## 8.2. Локальная система координат 
		Вокруг целевого сектора T находится 8 соседей. 
		Каждый сосед описывается ОП - фиксированным географическим направлением от T к соседу.
		0° = север
		Обозначение соседей по (dx, dz):
		-1:+1 (315°)    0:+1 (0°)     +1:+1 (45°)
		-1: 0 (270°)    T (n/a)       +1: 0 (90°)
		-1:-1 (225°)    0:-1 (180°)   +1:-1 (135°)
		ОП не зависит от ветра. Это просто геометрия.

		## 8.3. Относительные координаты
		ОК - это направление где СНВ смотрит в 0°.
		ОК(сосед) = (ОП(сосед) - СНВ + 360) mod 360

		## 8.4. Таблицы поправок
		Для каждого из 8 значений ОК задаются четыре таблицы (на глаз), по две на каждый тип соседа:
		Вода (ИНВ и ИСВ) - направление и ускорение:
		| ОК   	|    0°	|   45°	|  90°	| 135°	| 180°	|  225°	| 270°	| 315°	|
		| ИСВ	| -0,1	|  -0,2	| -0,15	|  0	| +0,1	| +0,15	| +0,1	|	0	|
		| ИНВ  	| -0,3 	|  -0,6	| -0,5	| -0,1	|   0	| +0,1	| +0,2	| +0,1	|
		Ландшафт (ИНЛ и ИСЛ) - направление и ускорение:
		| ОК	|   0°	|  45°	|  90°	| 135°	| 180°	| 225°	| 270°	| 315°	|
		| ИНЛ	| -0,5	| +0,4	| +0,3	| +0,2	| -1,0	| -1,2	| -0,9	| -0,7	|
		| ИСЛ	| -1,0	| -0,7	| -0,3	| +0,7	| +1,0	| +0,7	| -0,3	| -0,7	|
		Эти таблицы - эталон, работают для обоих полушарий одинаково.

		## 8.5. Расчёт поправок
		Полушарие задаёт знак для поправок направления:
			sign = северное ? -1 : +1
		Получение высоты:
			Для каждого соседа-земли:
				ΔH(сосед) = Hn(сосед) - Hn(T).
				Если ΔH > 0 - сосед выше цели.
				Если ΔH < 0 - сосед ниже.
			Для соседа-воды:
				hFactor = clamp(1.0 - Hs(T) / H_REF, 0.0, 1.0) (тут берется целевой сектор, ведь вода всегда 0)
				Если hFactor = 0 - влияние воды минимально
				Если hFactor = 1 - влияние воды максимально
				- Hs(T) - высота целевого сектора над waterLevel (0 для сектора на уровне моря).	
		Знак минус перед ИСВ/ИСЛ - уже в таблице, чтобы «пришло отрицательное - стало положительное».  
		Сосед земля выше цели - ускоряет поток. Если ΔH < 0 - тормозит.

		## 8.6. Сборка дневного (D) и ночного (N) состояний
		D/N отличаются правилом движения воздуха:
			- День: воздух движется с воды на сушу.
			- Ночь: воздух движется с суши на воду.
		Правило учёта соседей:
			В обеих фазах участвуют все 8 соседей. Разница в том, что днём эффект воды усиливается, 
			а ночью - ослабевает (и наоборот для суши). Это отражается через множитель:
			if (фаза == D):
				waterBoost = BOOST_DAY_WATER 1.2
				landBoost  = BOOST_DAY_LAND 1.0
			else:
				waterBoost = BOOST_NIGHT_WATER 0.8
				landBoost  = BOOST_NIGHT_LAND 1.2
			Итоговые поправки умножаются на соответствующий boost.
		Полный расчёт для одной фазы (D или N):
			### 8.6.1. Инициализация: vx = 0, vy = 0, ΔSpeed = 0
			
			### 8.6.2. Итоговый ветер:
				ОП = фиксированный угол (0/45/90/135/180/225/270/315)
				ОК = (ОП - СНВ + 360) mod 360
				idx = ближайший индекс из {0, 45, ..., 315} для ОК
				ΔH = Hn(сосед) - Hn(T)
				if сосед - вода:
					crossFactor = (targetIsWater && neighborIsWater) ? 0.6 : 1.0
					поправка = ИНВ(ОК) * sign * hFactor * waterBoost * crossFactor
				else:
					поправка = ИНЛ(ОК) * sign * ΔH * landBoost
				поправка - это угловое отклонение. Переводим в векторный сдвиг:
				vx += sin(deg2rad(поправка))
				vz = -cos(deg2rad(итоговое_направление))   // минус, потому что север — это -z
			Направление:
				angle_offset = rad2deg(atan2(vx, vy))
				итоговое направление для D/N = (СНВ + angle_offset + 360) mod 360
			Скорость:
				для каждого соседа-суши:
					ΔH = Hn(сосед) - Hn(T)
					итоговая_скорость_от_суши (ИСОС) += -ИСЛ[idx] * ΔH * 0.3 * landBoost
				для каждого соседа-воды:
					waterCrossFactor = (targetIsWater && neighborIsWater) ? 0.6 : 1.0
					итоговая_скорость_от_воды (ИСОВ) += -ИСВ[idx] * hFactor * 0.3 * waterBoost * waterCrossFactor
				итоговая скорость = СКСВ + ИСОС + ИСОВ
				итоговая скорость = clamp(итоговая скорость, WIND_MIN_SPEED, WIND_MAX_SPEED)
				
			### 8.6.3. Температура:
			Суточное колебание температуры зависит от:
				- широты (на экваторе меньше, у полюсов больше).
				- типа поверхности (вода сглаживает, суша усиливает).
				- времени суток (D - тепло, N - холодно).
				- lat - нормализованная широта
				lat = (z - equatorZ) / (polarZ - equatorZ)
				dailyAmplitudeFactor = targetIsWater ? 0.3 : 1.0 // Сглаживание суточной амплитуды над водой
				waterTempOffset = targetIsWater ? -WATER_TEMP_OFFSET : 0 // Общий сдвиг температуры воды вниз
				ΔT_lat = |lat| * TEMP_DAILY_AMPLITUDE * dailyAmplitudeFactor
				ΔT_day   = +ΔT_lat + waterTempOffset
				ΔT_night = -ΔT_lat + waterTempOffset
			Итоговая температура:
				T_day   = CT + ΔT_day
				T_night = CT + ΔT_night

		## 8.7. holdTime (УПВ)
		Параметр задаёт, сколько времени дневное и ночное состояния удерживаются вокруг своих пиков.
			- HOLD_BASE = 0.3 - минимальное удержание (примерно 2 часа);
			- HOLD_SCALE = 0.7 - размах;
			- stability_terrain - статическая устойчивость сектора из ландшафта (раздел # 8.8.).
		holdTime ∈ [0, 1]
		holdTime = 0   → D пик в 12:00, N пик в 00:00, без удержания
		holdTime = 0.5 → D пик с 10:30 до 13:30, N пик с 22:30 до 01:30
		holdTime = 1   → D пик с 09:00 до 15:00, N пик с 21:00 до 03:00
		WG вычисляет holdTime для каждого сектора и сохраняет его. 
		Формула:
			holdTime = clamp(HOLD_BASE + stability_terrain * HOLD_SCALE, 0, 1)
		WET использует holdTime для интерполяции между пиками D и N во время суток.

		## 8.8. stability_dynamic (УП)
		Параметр задаёт, насколько сильно WET может отклонять погоду от сохранённого значения во время игры.
		stability_dynamic ∈ [0, 1]
			- 1.0 WET использует значения как есть, без шума
			- 0.0 WET добавляет случайные отклонения вплоть до ±40° по направлению
		WG вычисляет stability_dynamic по двум компонентам:
			Компонент A - геометрический (статический).
				waterNeighbors = количество соседей, у которых тип поверхности = вода
				heightVariance = среднее от |ΔH| по всем 8 соседям
				stability_terrain = 1 - (waterNeighbors * 0.1 + heightVariance * 0.01)
				stability_terrain = clamp(stability_terrain, 0, 1)
			Компонент B - динамический (зависит от сезонных данных).
				Для расчёта отклонения направления от сезонного используется функция angularDiff(a, b),
				возвращающая знаковую разницу углов в диапазоне [-180, +180]:
					angularDiff(a, b) = ((a - b + 540) mod 360) - 180
				Свойства:
					- angularDiff(a, b) = 0,   если направления совпадают
					- angularDiff(a, b) = +90, если a на 90° по часовой от b
					- angularDiff(a, b) = -90, если a на 90° против часовой от b
					- результат всегда в диапазоне [-180, +180]
					- функция симметрична: angularDiff(a, b) = -angularDiff(b, a)
				deviation = max(|angularDiff(direction_D, СНВ)|, |angularDiff(direction_N, СНВ)|)
				stability_seasonal = (deviation > 135) ? 1 - (deviation-135)/45 : 1 - deviation/135
			Итоговая устойчивость:
				stability_dynamic = stability_terrain * stability_seasonal
			Сохраняется в SectorClimate вместе с TDW D и TDW N.
		Как WET применяет:
			noise_angle = (1 - stability_dynamic) * 40 * rand(-1, 1)
			noise_speed = (1 - stability_dynamic) * 0.5 * rand(-1, 1)

		## 8.9. Направление суточного разворота
		Направление суточного разворота определяет, в какую сторону происходит переход от дневного пика к ночному. 
		То есть при интерполяции между TDW D и TDW N направление меняется по кратчайшему пути в заданную сторону:
			- в северном полушарии - против часовой;
			- в южном - по часовой.
		Практически, если разница между direction_D и direction_N больше 180°, а полушарие северное - WET берёт не короткий 
		путь, а длинный (против часовой). Это даёт эффект «закрутки» в течение суток.
		Формула в WET:
			delta = direction_N - direction_D
			если полушарие северное:
				если delta > 0: delta -= 360
			если полушарие южное:
				если delta < 0: delta += 360
			direction(t) = direction_D + delta * f(t)
		Где f(t) - интерполяционный коэффициент от 0 (полдень) до 1 (полночь).
		WG не сохраняет это правило - оно выводится из данных сектора (полушарие) на стороне WET.

		## 8.10. Результат
		Для каждого из 12 сезонных состояний сектора WG сохраняет 4 итоговых набора и 2 параметр:
			- TDW_D - дневные temperature, direction, speed;
			- TDW_N - ночные temperature, direction, speed;
			- holdTime - устойчивость по времени (0..1);
			- stability_dynamic - устойчивость погоды (0..1).
			- sign - полушарие
			- Hs - высоту сектора от которой WET считает погоду для игрока.
		Итого на сектор: 
			Сезонных: 12 × (2 × TDW + holdTime + stability_dynamic) = 96
			Секторных: sign + Hs = 2
		Все они сохраняются в weather - файл в структуре SectorClimate.

	# 9. Влажность 
		Для каждого сектора и каждого из 12 сезонных состояний (yearType × season) WG рассчитывает локальную влажность
		humidity ∈ [0, 1].
		Влажность - отдельный итоговый параметр сектора, не зависящий от суточного расчёта. 
		Она используется в разделе # 10. для определения возможных природных явлений: rain, snow, fog, storm.
		Влажность вычисляется после сезонного прохода и не влияет на температуру, ветер или устойчивость. 
		Это финальный климатический параметр.
		Из глобальных настроек мира:
			- GLOBALHUMIDITY ∈ [-1, +1] - задаётся игроком.

		## 9.1. Факторы влажности
		Локальная влажность складывается из шести факторов.
			### 9.1.1. Базовый уровень по широте
				Экватор влажнее полюсов.
				baseHumidity = 1 - |lat| * 0.5
				- Экватор (lat = 0) → 1.0
				- Полюс (lat = ±1) → 0.5
			Глобальная настройка мира модулирует базовый уровень:
			baseHumidity *= (1 + GLOBALHUMIDITY * 0.5)
				- GLOBALHUMIDITY = -1 → базовый уровень уменьшается вдвое;
				- GLOBALHUMIDITY = 0 → без изменений;
				- GLOBALHUMIDITY = +1 → базовый уровень растёт в полтора раза.

			### 9.1.2. Температурный фактор (испарение)
			Чем жарче - тем больше испарение. Ниже точки замерзания испарения нет.
			tempFactor = clamp((СТ - TEMP_FREEZE) / (TEMP_HOT - TEMP_FREEZE), 0, 1)
			СТ берётся из того же сезонного состояния, для которого рассчитывается влажность.

			### 9.1.3. Наличие воды рядом
			Считается количество соседей-воды в радиусе 1.
			waterCount = количество соседей с типом поверхности "вода"
			waterFactor = waterCount / 8
			Для воды в радиусе 0, waterFactor = 0. Для сектора, окружённого водой, waterFactor = 1.

			### 9.1.4. Наветренность
			Влажность приносится ветром. Соседи-вода, находящиеся против ветра (с наветренной стороны), влияют сильнее. 
			Соседи-вода по ветру - слабее.
			Для каждого соседа-воды определяется его ОК (относительная координата из раздела # 8.3):
			ОК(сосед) = (ОП(сосед) - СНВ + 360) mod 360
				- ОК = 180° - сосед точно против ветра (с наветренной стороны, максимальное влияние);
				- ОК = 0° - сосед точно по ветру (с подветренной стороны, минимальное влияние);
				- ОК = 90° или 270° - боковой ветер, среднее влияние.
			Коэффициент наветренности для одного соседа:
				windwardWeight(ОК) = (1 + cos(deg2rad(ОК - 180))) / 2
			Свойства:
				- ОК = 180° → windwardWeight = 1.0 (максимум);
				- ОК = 0° → windwardWeight = 0.0 (минимум);
				- ОК = 90° или 270° → windwardWeight = 0.5.
			Итоговый коэффициент наветренности:
				windwardFactor = (Σ по соседям-воде windwardWeight(ОК)) / 8
			Нормируется на 8 (общее число соседей), чтобы диапазон оставался [0, 1].

			### 9.1.5. Фактор рельефа (высота)
			Высокие сектора удерживают меньше влаги (разрежённый воздух, сток воды).
			heightPenalty = clamp(Hs / HUMID_H_REF, 0, 1)
			reliefFactor = 1 - heightPenalty * 0.5
				- Hs = 0 → reliefFactor = 1.0 (низменность удерживает влагу);
				- Hs = 80 → reliefFactor = 0.5 (высокогорье удерживает вдвое меньше);
				- Hs > 80 → reliefFactor продолжает падать, но не ниже 0.5.
			
			### 9.1.6. Множитель скорости ветра
			Чем сильнее ветер, тем быстрее влага уносится из сектора.
			windDrain = 1 - СКСВ * WIND_DRAIN_RATE
				- СКСВ = 0 → windDrain = 1.0 (штиль, влага удерживается);
				- СКСВ = 1 → windDrain = 0.7 (сильный ветер, влага уносится);
				- СКСВ > 1 → windDrain продолжает падать, но clamp(windDrain, 0.3, 1.0).

		## 9.2. Формула
		Итоговая влажность сектора для одного сезонного состояния:
		humidity = baseHumidity * tempFactor * (waterFactor + windwardFactor) * reliefFactor* windDrain
		humidity = clamp(humidity, 0, 1)
		Сумма (waterFactor + windwardFactor) может превысить 1, если сектор окружён водой и вода преимущественно наветренная. 
		Это допустимо: clamp в конце обрежет.

		## 9.3. Результат
		Для каждого сектора WG сохраняет 12 значений влажности - по одному на каждое сезонное состояние (yearType × season).
		Структура в SectorClimate:
		humidity[yearType][season] ∈ [0, 1]
		Итого на сектор: 
			- 96 сезонных
			- 2 секторных 
			- 12 значений влажности.
		Общее количество: 110 значений на сектор.

	# 10. Природные явления
		После расчёта температуры, ветра и влажности WG проходит по карте и определяет, какие природные явления потенциально 
		возможны в каждом секторе для каждого сезона.
		Результат работы - единый список кластеров. 
		Кластер - это группа соседних секторов с одним типом явления, действующая в одном сезоне, одном типе года и 
		одном полушарии.
		Кластеры - это не «флаги на сектор», а отдельные сущности. 
		WET во время игры работает именно с кластерами: выбирает до одного активного кластера на полушарие, 
		роллит интенсивность и решает, когда явление начнётся и закончится.

		## 10.1. Типы явлений
		Четыре типа:
			- rain - дождь;
			- snow - снег;
			- fog - туман;
			- storm - буря (пыльная / песчаная).
		Каждый кластер имеет ровно один тип явления.

		## 10.2. Условия появления явления в секторе
		Для каждого из 12 сезонных состояний (yearType × season) сектор проверяется на соответствие условиям каждого типа явления.
		Условия простые и независимые.
			### 10.2.1. Дождь (rain)
			Условие:
			- humidity > HUMID_RAIN_MIN;
			- СТ > TEMP_FREEZE;
			- СКСВ < WIND_RAIN_MAX.

			### 10.2.2. Снег (snow)
			Условие:
			- humidity > HUMID_SNOW_MIN;
			- СТ < TEMP_SNOW_MAX.

			### 10.2.3. Туман (fog)
			Условие:
			- humidity > HUMID_FOG_MIN;
			- СКСВ < WIND_FOG_MAX.

			### 10.2.4. Буря (storm)
			Условие:
			- поверхность сектора или одного из соседей - песок;
			- humidity < HUMID_STORM_MAX;
			- СТ > TEMP_FREEZE;
			- СКСВ > WIND_STORM_MIN.
		Условия разных явлений могут пересекаться: один сектор может одновременно подходить под дождь и под туман. 
		Это нормально - кластеризация идёт отдельно для каждого явления.
		Если сектор не подходит ни под одно условие - он не участвует в кластеризации.

		## 10.3. Кластеризация
		Кластеризация выполняется отдельно для каждого явления в каждом сезоне.
		Для одного сезона и одного типа явления:
			1. Отбираются все сектора, подходящие под условия этого явления (раздел # 10.2.).
			2. Запускается flood fill по 8 соседям: соседние сектора с тем же типом объединяются в кластер.
			3. Кластеры размером меньше REGION_MIN_SIZE = 8 отбрасываются.
			4. Оставшиеся кластеры фиксируются в общем списке.
		Затем процедура повторяется для следующего типа явления. Сектора, вошедшие в кластеры одного явления,
		не исключаются из обработки других явлений - они могут одновременно принадлежать кластерам разных типов, 
		если подходят под их условия.
		Правило пересечения: кластеры разных типов могут пересекаться в одном секторе. Кластеры одного типа не пересекаются 
		по построению - flood fill объединяет соседние сектора одного типа в один кластер.
		Правило сезонов: каждый кластер существует ровно в одном сезоне. Весенний дождь и летний дождь на одних и тех 
		же секторах - два разных кластера.
		Несколько несоприкасающихся кластеров одного явления в одном сезоне - норма. Два дождевых кластера в разных углах
		карты существуют как отдельные записи. WET может запустить дождь сначала в одном, потом в другом.

		## 10.4. Расширение кластера
		После формирования кластеров выполняется расширение - имитация прохода Циклона вокруг каждого кластера.
		Правило:
			- для каждых 3 секторов кластера добавляется 1 случайный соседний сектор;
			- сосед берётся случайный из тех, что граничат с кластером;
			- тип явления у добавленного сектора = тип явления кластера;
			- без дополнительных условий (горы, высоты) - просто случайность для аномалий;
			- добавленный сектор может ранее принадлежать другому кластеру - тогда он принадлежит обоим.
				Разные явления - допустимо.
				Если выбранный сектор уже добавлен в другой кластер с тем же phenomenon и season, 
				выбор повторяется - берётся другой граничный сектор.

		## 10.5. Интенсивность
		Интенсивность - это множитель intensity ∈ [0.3, 1.0], который WET использует для масштабирования силы явления.
		Интенсивность определяется по формуле от центра кластера к краям.
			- центр кластера - геометрический центр (среднее арифметическое координат всех клеток кластера);
			- расстояние от центра до каждой клетки считается в радиусах: radius кластера = максимальное расстояние от центра до клетки;
			- самая дальняя клетка получает intensity = 0.3;
			- центральная клетка получает intensity = 1.0.
		Формула для клетки c:
		distance(c) = расстояние от центра кластера до c
		radius      = максимальное distance по всем клеткам кластера
		intensity(c) = 1.0 - (distance(c) / radius) * 0.7
		Свойства:
			- distance = 0 → intensity = 1.0;
			- distance = radius → intensity = 0.3;
			- промежуточные - линейно.
		Также каждый кластер хранит общий размер (totalCells). 
		WET использует его для выбора базовой интенсивности: чем больше кластер, тем выше шанс получить сильное явление, 
		но с элементом случайности для аномалий (локальный шторм в большом кластере).

		## 10.6. Формат хранения
		Кластеры хранятся в едином списке в weather-файле.
		Структура:
		regions = [{
			id: 1,
			phenomenon: "rain",
			season: "summer",
			yearType: "normal",
			hemisphere: "north",
			totalCells: 14,
			center: { x: 5, z: 3 },
			cells: [
				{ x: 4, z: 2, intensity: 0.85 },
				{ x: 5, z: 2, intensity: 0.92 },
				{ x: 6, z: 2, intensity: 0.85 },
				...
			]
		},{
			id: 2,
			phenomenon: "snow",
			season: "winter",
			yearType: "cold",
			hemisphere: "south",
			totalCells: 22,
			center: { x: 12, z: 9 },
			cells: [...]
		},...]
		Поля:
			- id - уникальный идентификатор кластера;
			- phenomenon - тип явления (rain / snow / fog / storm);
			- season - сезон, в котором кластер активен (spring / summer / autumn / winter);
			- yearType - тип года (normal / hot / cold);
			- hemisphere - полушарие (north / south);
			- totalCells - общее количество клеток в кластере;
			- center - координаты геометрического центра;
			- cells - список клеток с координатами и множителем интенсивности.
		Обратная связь «сектор → кластеры» не хранится. WET при необходимости находит активные кластеры фильтрацией списка.

		## 10.7. Результат
		Для каждого типа года и каждого сезона WG формирует список кластеров.
		Итоговая структура в weather-файле:
			regions[] - единый список всех кластеров по всем 12 сезонам
		Количество кластеров заранее неизвестно, зависит от карты.

		WET во время игры:
		1. Определяет текущий тип года и сезон.
		2. Определяет текущее полушарие по позиции игрока.
		3. Фильтрует regions по yearType, season, hemisphere.
		4. Случайно выбирает до одного активного кластера на полушарие.
		5. Роллит интенсивность явления с учётом totalCells и множителя клетки игрока.
		6. Запускает явление и держит его ограниченное время.
		
		Нажатие переключает режим отображения и переоткрывает меню.
